## 2. 무엇을 만들었나

### 공통
- `app/scoring/` 새 패키지 — DB·모델을 읽는 스코어러와 결선. `app/views/` 는 계속 stdlib 순수 함수만 둔다(CLAUDE.md 규칙). bridge 는 실물을 **호출 시점에 지연 import** 해서 bridge import 만으로 DB·LightGBM 이 끌려오지 않는다.
- `app/scoring/schedule.py` — 워크포워드 달력. 확정 규칙(expanding · 20거래일마다 재학습 · embargo 20)을 **첫 거래일부터 20거래일 간격의 고정 격자**로 구현했다. 격자가 실행과 무관하므로 같은 as_of 는 언제나 같은 cutoff → 같은 모델이고, 그래서 모델을 cutoff 로 캐시해도 재현성이 깨지지 않는다. 두 관점이 같은 달력을 쓴다.
- `app/views/calibration.py` — isotonic 보정(PAV) stdlib 구현. 두 관점 공용.
- 데이터 적재: price_daily 109,704행(73종목, 2019-01-02~2025-12-30), 거시지표 2019~2025, 국면 스냅샷 2,557건. (DB 가 비어 있어 다시 넣었다. FRED 키가 `.env` 에 비어 있어 공개 CSV 경로로 넣었다 — 정식 경로와 값이 같음을 09-27 에 확인한 경로다.)

### T3 시장분석
- 표본: `views/market/dataset.py` — t 에서 끝나는 직전 120행 창으로 피처(bridge 와 같은 규칙), 라벨은 `labels.make_label` 재사용, 라벨 확정일(t+20행) ≤ cutoff 인 것만.
- 학습: `scoring/market_model.py` — `seed=42 · deterministic · num_threads=1 · force_row_wise`. 학습 창 끝 20% 를 보정 구간으로 떼고 그 사이에 embargo 20거래일. 결측 피처는 NaN 그대로.
- 추론: 보정확률 p → `raw_score = 2p − 1`, SHAP 상위 3개를 `evidence["shap"]`.
- 유니버스: 원장 활성·비레버리지 전체(스펙 무관 → 모델을 스펙 사이에 재사용).
- 러너는 종가만 넘겨 `atr_14_pct`·`volume_ratio_20` 이 비는데, 모델은 진짜 OHLCV 로 배웠으므로 그 둘만 저장소 일봉으로 같은 규칙으로 다시 계산해 채운다.
- 모델 등록: `train_model` 태스크 → MinIO `models` 버킷 → `ml_models` (`is_active` 전환을 한 트랜잭션으로).

### T4b 시장온도
- 규칙: `raw = 2·P(사건 | 묶음, 국면) − 1`. 묶음 = 자산군(EQUITY/BOND/COMMODITY), 인버스는 따로. P = cutoff 까지 실현된 표본의 라플라스 평활 빈도. unknown 국면·자산군 없는 종목은 중립.
- 이어서 isotonic 보정. 빈도표·보정기는 cutoff 마다 한 번 만든다(cutoff 하나 약 0.2초, 백테스트 1회 분량 86 cutoff 에 16.7초).

### T6·T10 라이브 결선
- `daily_judge(portfolio_id, as_of)`: 스펙 종목 → 가격 창 → bridge 의 피처 규칙·`SCORERS` 그대로(`BacktestJudge` 를 상속해 가중치 출처만 DB 로 바꿈) → `get_view_weights`(strict <, 없으면 FN-409 1/3) → `integrate` → **IntegratedSignal 에서 멈춤**. `decision_records`(mode='live') 한 행 + `view_scores` 를 한 트랜잭션으로 적재. M2 칸(risk_caps 이하)은 비워 둔다.
- `update_view_weights(portfolio_id, as_of)`: 전날까지 실현이 확정된 판단을 채점 → `view_performance` (hit_rate·contribution, 멱등) → 최근 60개 판단의 관점별 Brier → `hedge.rolling_weights` → `insert_view_weights`.
- `calibrated_prob`(계약 ②) ↔ `calibrated_score`(DB 컬럼) 변환을 `decisions.py` 두 함수에만 둠.

### 백테스트 ↔ 브리핑 데이터
- `BacktestJudge.last_views()` 를 러너의 리밸런싱 결정마다 `decisions[i].views = {weights, probs}` 로 싣는다. 스키마 변경 없이 기존 `backtest_metrics.window_results` 로 저장되고 `GET /backtest/runs/{id}` 가 그대로 돌려준다.

- `/report` 의 시각 언어(색 토큰·Pretendard·등폭 숫자)를 `components/flow.css` 로 끌어올려 흐름 화면 18개에 적용. 7단계 진행 레일, 버튼 4종, 상태 표시(로딩·알림·빈 상태) 통일, 640px 이하 대응. **동작·API·라우팅·문구는 그대로** 두고 표현만 바꿨다.

## 3. 기술 선택과 이유 (비교 검증 결과)

| 결정 | 후보 | 측정 | 선택 · 이유 |
|---|---|---|---|
| isotonic 보정 구현 | scikit-learn `IsotonicRegression` vs 직접 PAV | 무작위 300세트 대조 최대 차 **2.2e-16** | **직접 PAV** — `app/views/` 는 stdlib 만 쓸 수 있고, 시장온도는 ML 의존성 없이 돌아야 한다. 값이 같으므로 잃는 것이 없다. 대조는 `requires_ml` 테스트로 고정 |
| SHAP 계산 | `shap.TreeExplainer` vs LightGBM `predict(pred_contrib=True)` | 2,680행 최대 차 **4.4e-16**, 상위 3 피처 2680/2680 일치. shap 0.51 은 LightGBM 에 대해 내부적으로 pred_contrib 에 위임 | **pred_contrib** — 같은 TreeSHAP, shap import 가 사라짐 |
| MinIO 클라이언트 | `minio` 7.2 vs `boto3` | 새로 깔리는 설치 크기 약 13MB vs 약 30MB(botocore 27MB), import 0.075s vs 0.126s, 코드 길이 같음 | **minio** — 버킷 하나에 put/get 만 하는 용도라 boto3 의 범용성이 필요 없다 |
| 시장온도 규칙 | 기저율 상수 / 자산군 고정 부호(주식 +intensity, 채권 −0.5·intensity) / 국면 조건부 빈도 | 워크포워드 보정 후 Brier (2020~2025, 96,270표본): 상수 0.2399 · 고정 부호 **0.2456** · 조건부 **0.2384**. 2023~ 구간: 0.2302 · 0.2331 · 0.2252 | **조건부 빈도** — 고정 부호는 두 구간 모두 기저율보다 나빴다(이 기간 채권 ETF 가 국면과 무관하게 대체로 올라 "risk_on 이면 채권 하락"이 틀린 쪽에 걸렸다). 기저율을 넘은 것은 조건부 빈도뿐. 오케스트레이터가 같은 데이터로 다시 재서 확인 |
| 시장온도 캐시 | cutoff 별 전체 재계산 vs 증분 쌍 캐시 | 전체 재계산으로 86 cutoff 16.7초 | **전체 재계산** — 충분히 빠르고, 증분 캐시는 코드가 1.5배로 늘었다 |
| 스코어러 배치 | `app/views/` 안 vs 새 `app/scoring/` | — | **분리** — views 는 stdlib 순수 함수 규칙을 지키고, DB·LightGBM 을 읽는 쪽은 scoring 에. bridge 는 지연 import 로 연결 |
| 라이브 판단 기록 | Q3 마이그레이션까지 미연결(계획서 원안) vs 라이브 모드만 지금 연결 | — | **라이브 모드 연결** — 실제 portfolio_id 가 있어 지금 스키마로 FK 가 성립한다. Q3 가 필요한 건 portfolio 없는 백테스트 모드(run_id 축)뿐이라 그쪽은 손대지 않았다 |
| 브리핑 데이터 경로 | 새 표·API vs 백테스트 결과 JSON 에 싣기 | — | **결과 JSON** — 스키마 변경 없이 기존 `GET /backtest/runs/{id}` 로 끝난다 |

## 6. 작업 방식

- 멀티 에이전트: 오케스트레이터(공통 기반·통합·검증) + 에이전트 4개(시장분석 / 시장온도 / 라이브 결선 / 프론트 UI·UX) 병렬, 이어 code-simplifier 정리와 code-review.
- 사용한 스킬: `frontend-design`(UI/UX), `dataviz`(차트 색 검증), `code-simplifier`, `code-review`, `claude-md-management`(CLAUDE.md 갱신).
- 에이전트 보고는 그대로 믿지 않았다. 파일이 실제로 있는지, 테스트·수치가 맞는지를 오케스트레이터가 직접 다시 돌려 확인했다(시장온도 규칙 비교는 다시 재서 확인했고, 테스트 3개 파일은 직접 썼다).
