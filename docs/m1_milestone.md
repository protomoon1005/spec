## 목표

- 사용자가 쓴 문장을 **전략서(Spec JSON)** 로 바꾸고, 그 결과를 데이터베이스에 남기는 것까지
- 전략서가 지켜야 할 범위(성향별 종목 상한)는 **만들 때부터 박아 넣는다**

### M1 이 끝났다고 말할 수 있는 조건

- 자연어 한 줄을 넣으면 → 성향에 맞는 전략서가 나오고 → 데이터베이스에 저장된다
- 샘플 10건이 전부 통과한다
- 같은 입력을 두 번 넣으면 같은 후보 종목과 같은 허용범위가 나온다
  - LLM 출력 자체는 흔들릴 수 있지만, **후보 선정과 범위 계산은 흔들리면 안 된다**

### ② 비중 클램프 — **Validator 담당으로 확정**

- 경계가 이렇게 나뉜다
  - **M1** — 프리셋을 스키마에 박아 넣어 **애초에 못 어기게** 한다
  - **Validator** — 하드캡으로 **접는다.** 접었다는 사실(`was_adjusted`)도 여기서 남긴다
- M1 은 5단계에서 파싱과 저장까지만 한다. 원출력과 확정값이 같고 `was_adjusted=false` 로 들어간다
- **남은 구멍: Validator 본체가 아직 없다.** 인터페이스조차 없다.
  데모까지 안 나오면 **하드캡을 넘는 전략서가 그대로 저장된다.**
  언제 누가 만들지 확인할 것

### ③ 되묻기 대화 상태 — **Redis. 메모리는 안 된다**

- 메모리(파이썬 변수)가 안 되는 이유: **프로세스가 다르다**
  - 컴파일은 Celery 작업이라 `worker` 컨테이너에서 돈다
  - 사용자 응답은 `api` 컨테이너로 들어온다
  - 되묻기는 "worker 가 묻고 → 사용자가 api 로 답하고 → worker 가 이어받는" 왕복이라
    정확히 여기서 막힌다. 거기다 `--reload` 라 코드를 고칠 때마다 날아간다
- Redis 가 원하던 장점을 그대로 가져간다
  - **표를 추가하지 않는다** — 전원 데이터베이스 날릴 일 없음
  - 이미 떠 있고(Celery 가 쓰는 중) 패키지도 깔려 있다(헬스체크가 쓴다)
  - 프로세스가 달라도 공유된다. 만료를 걸어 버려진 대화가 쌓이지 않게 한다
- 구현은 `set(키, JSON, 만료 30분)` / `get(키)` 두 줄 수준

### ④ 파이프라인 라이브러리 — **M1 전용 묶음으로**

- `pyproject.toml` 에 `m1` 묶음을 판다
- **다만 이미지 분리가 아니다.** api·worker·beat 가 Dockerfile 하나를 공유하고
  팀이 안 쪼개기로 했다. `.[dev,m1]` 로 깔면 세 컨테이너에 전부 들어간다
- 얻는 것은 "안 깔고도 앱이 뜬다" 와 "CI 는 `.[dev]` 만 깔아 M1 테스트를 마커로 뺀다"
- LangGraph 는 순수 파이썬이라 용량 부담이 거의 없다
- **격리의 실체는 의존성보다 디렉터리와 접점**이다. `app/m1/` 한 곳에 몰고
  태스크 함수 안에서 import 한다

### ⑤ 거절 장면용 종목 — **넣지 않기로 했다** (2026-09-20 철회)

- 한때 레버리지·상장폐지 종목을 시드에 넣었다가 **지웠다.** 수집 스크립트가 일부러
  걸러내는 종목이라 원장에 상주할 이유가 없고, 상장폐지 종목은 실제 폐지 종목을
  확인할 경로가 없어 지어낸 값이었다
- **막는 규칙 자체는 그대로 동작하고 테스트도 남아 있다.** 필요한 종목은
  `tests/conftest.py` 의 `blocked_etfs` 픽스처가 그때그때 넣고 지운다 —
  테스트 데이터는 테스트 안에 있는 게 맞다
- 데모에서 "규칙이 막았다" 장면을 보이려면 그때 몇 줄을 다시 넣으면 된다.
  지금 원장에 없으면 "그런 종목을 못 찾았습니다" 가 나온다는 점만 기억할 것

### 사본을 지우려던 계획을 바꿨다

착수하면서 `policy.py` 호출부를 보니 **지우면 백테스트가 깨진다.**

- `scripts/run_backtest_vbt.py` 와 타입스크립트 러너는 **데이터베이스 없이 표 파일만으로 돈다**
- `policy.py` 를 DB 조회로 바꾸면 백테스트에 postgres + 시드가 필수가 된다
- 타입스크립트 쪽은 여전히 파일이라, 파이썬만 DB 를 보면 두 러너 대조의 전제가 깨진다
- 브라우저와 오프라인 스크립트는 DB 를 직접 못 읽는다. **"전부 DB 조회" 가 자명한 답이 아니다**

그래서 **사본을 지우지 않고 어긋남을 테스트로 막았다.**

```
데이터베이스 ↔ policy.py   새 테스트 8개
policy.py ↔ policy.ts      기존 두 러너 대조 (값이 틀리면 주문이 달라진다)
```

세 벌을 한 곳으로 합칠지, 합친다면 파일을 생성해서 둘지 런타임에 읽을지는
백테스트 담당과 정할 문제로 남겼다.

## 3단계 — BBL (블록 라이브러리)  ✔ 완료 2026-09-20

### BBL 이 실제로 무엇인가

블록 라이브러리는 **전략서에 들어갈 수 있는 값들의 목록**이다.

전략서 계약(`contracts/spec.py`)에 `# TODO: 값 집합은 BBL 확정 후 M1` 주석이 일곱 군데
달려 있다. 자리와 타입은 고정됐는데 **어떤 값이 허용되는지가 비어 있다.**
그 빈칸을 채우는 것이 3단계다.

- `rebalance.trigger.type` · `freq` · `day` — 지금은 아무 문자열이나 정수
  - 리밸런싱 블록이 허용값을 정한다
- `signal_rules.market_analysis.indicators[]` — 지금은 아무 문자열
  - 지표 블록 9개가 허용값을 정한다
- `signal_rules.sentiment.target_sectors[]` — 지금은 아무 문자열
  - 업종 묶음 7개가 허용값을 정한다
- `signal_rules.market_temperature.trend_index` · `volatility_index` — 지금은 아무 문자열
  - 거시지표 블록이 허용값을 정한다

**즉 BBL 은 "자연어를 무엇으로 번역할 수 있는가" 의 사전이다.** 사전에 없는 말은
전략서에 못 들어간다.

### 블록 식별자 규약

- **지표 블록은 식별자가 곧 전략서에 들어갈 값이다.** `ret_20` 블록을 고르면
  `indicators` 에 `"ret_20"` 이 그대로 들어간다. 번역표를 따로 두지 않는다
- 나머지는 접두어를 붙인다 — `RB_`(리밸런싱) · `FL_`(필터) · `ET_`(ETF 특성)
- 이유: 지표는 이미 `features.py` 가 이름을 정해 뒀고, 그 이름이 판단 계층이
  실제로 쓰는 이름이다. 다른 이름을 붙이면 변환이 한 겹 생기고 언젠가 어긋난다

### 블록 종류별 시드 (다섯 중 넷만 채운다)

**① 지표 `indicator` — 11개**

- 가격 지표 9개는 `features.py` 의 피처셋 `v0.1-ta9` 그대로
  `ret_1` · `ret_5` · `ret_20` · `ma_gap_20` · `ma_gap_60` · `rsi_14` · `atr_14_pct` ·
  `vol_20` · `volume_ratio_20`
- 거시지표는 **둘만** — `KOSPI200`(추세 지수) · `VIX_CLOSE`(변동성 지수)
  - 처음엔 수집 중인 넷을 다 넣으려 했는데, 전략서의 `market_temperature` 에는
    자리가 둘뿐이다. 환율과 신용 스프레드는 국면 판정이 내부에서 쓰는 입력이고
    전략서에 자리가 없다 — 넣으면 잘못된 자리에 박힐 수 있다
  - `macro/codes.py` 가 이미 `TREND_INDEX_CODES` · `VOLATILITY_INDEX_CODES` 로
    같은 구분을 해 두고 있었다. 그 상수로 테스트를 고정했다
- **없는 이름을 넣지 말 것.** 예시 파일에 있던 `momentum_20d` · `VKOSPI` 는
  계산하지도 수집하지도 않는다. 넣으면 판단 계층이 그 값을 못 찾는다
- 지표를 늘리려면 피처셋 버전을 올려야 하고 그건 M3 영역이다

**② 리밸런싱 `rebalance` — 6개**

- `RB_MONTHLY_FIRST` 월 첫 거래일 · `RB_MONTHLY_MID` 월 중순
- `RB_QUARTERLY` 분기 첫 거래일 · `RB_WEEKLY` 주 1회
- `RB_THRESHOLD_5` 비중이 5%p 벗어나면 · `RB_SIGNAL` 신호가 바뀌면
- 각 블록의 `params_schema` 에 전략서에 박힐 모양을 그대로 담는다
  예: `{"type": "calendar", "freq": "monthly", "day": 1}`
- **하드캡의 최소 간격(5일)보다 짧은 주기는 넣지 않는다.** 넣어 봐야 나중에 접힌다

**③ 필터 `filter` — 8개 내외**

- 후보 종목을 추리는 조건. 자연어의 "~만" / "~빼고" 에 대응한다
- 예: `FL_NO_LEVERAGE` 레버리지·인버스 제외 · `FL_DOMESTIC_ONLY` 국내만 ·
  `FL_BOND_ONLY` 채권만 · `FL_LARGE_ONLY` 순자산 상위만
- `params_schema` 에 어느 칸을 어떻게 거르는지 담는다
  예: `{"column": "group_id", "op": "eq", "value": "BOND"}`
- **종목 표에 실제로 있는 칸만 쓴다** — 종목코드·이름·업종·자산군·위험등급.
  보수율·최대낙폭은 비어 있어서 지금은 거를 수 없다

**④ ETF 특성 `etf_trait` — 8개 내외**

- 종목 이름에서 읽히는 성격. 자연어의 "배당주로" / "환헤지 된 걸로" 에 대응한다
- 예: `ET_DIVIDEND` 배당 · `ET_COVERED_CALL` 커버드콜 · `ET_HEDGED` 환헤지(H) ·
  `ET_TR` 분배금 재투자 · `ET_ACTIVE` 액티브
- 판정은 종목명 문자열 규칙이다. `build_universe.py` 의 업종 분류와 같은 방식이고,
  거기 있는 정규식을 참고하되 **종목 표에 칸을 추가하지 않는다**

**⑤ 렌즈 `lens` — 보류**

- 감성 분석이 기사를 어느 관점으로 읽을지를 가리키는 블록이다
- 감성 점수 모델 자체가 아직 없고 렌즈 목록 정의도 없다. **M3 와 조율 전까지 비워 둔다**

### 태그 체계

- `bbl_tags` 는 `(블록, 태그)` 평면 표다. 계층도 이름공간도 표가 주지 않는다
- 표에 칸을 추가하지 않는다는 규칙이 있으므로 **접두어 규약으로 푼다**

**접두어 다섯 개로 고정한다. 늘리지 않는다.**

- `kw:` — 사용자 문장에서 바로 잡히는 한국어 말
  - `kw:배당` · `kw:안전하게` · `kw:반도체`
- `asset:` — 자산군
  - `asset:equity` · `asset:bond` · `asset:commodity`
- `sector:` — 업종 6개
  - `sector:semiconductor` · `sector:battery` · `sector:biohealth` ·
    `sector:finance` · `sector:internet_platform` · `sector:consumer`
- `country:` — 국가
  - `country:kr` · `country:us` · `country:other`
- `risk:` — 위험 성향 연관
  - `risk:low` · `risk:mid` · `risk:high`

**값이 닫힌 것과 열린 것**

- `asset:` · `sector:` · `country:` 는 **닫혀 있다.** `asset_groups` 표의 12개가 전부고
  더 늘지 않는다. 지어내면 종목을 거를 때 안 맞는다
- `risk:` 도 세 개로 닫는다. 성향은 5단계지만 블록과의 연결은 느슨해서
  ("보수적인 쪽" 정도지 "성향 2 전용"이 아니다) 셋이면 충분하다
- **`kw:` 만 열려 있다.** 위 세 개는 예시이고, 블록마다 1~3개씩 붙어 40~60개쯤 된다.
  시드를 쓰면서 확정한다

**`kw:` 는 사용자 원문과 맞추는 게 아니다**

- 사용자가 쓰는 말은 무한하다. "배당" / "배당금" / "월배당" / "따박따박 나오는" 을
  태그로 다 쫓으면 끝이 없다
- **5단계에서 LLM 이 뽑아낸 표준 키워드와 맞춘다.** 표현의 다양함은 LLM 이 흡수하고
  태그는 표준 낱말만 들고 있는다

```
"따박따박 돈 나오는 걸로 안전하게"
        ↓  의도 추출 (5단계, LLM)
{ 키워드: ["배당", "안전하게"] }
        ↓  태그 매칭 (3단계, 검색 함수)
ET_DIVIDEND · FL_NO_LEVERAGE
```

- 벡터 검색이 필요해지는 건 **LLM 이 뽑은 키워드조차 사전에 없을 때**다

**규칙**

- 접두어와 값은 전부 소문자. `kw:` 값만 한국어 원문 그대로 쓴다
- `asset:` · `sector:` · `country:` 의 값은 **`asset_groups.group_id` 를 소문자로
  바꾼 것**이어야 한다. 새로 지어내지 않는다 — 종목을 거를 때 바로 맞춰 쓸 수 있고,
  어긋나면 테스트가 잡는다
- 한 블록에 태그를 다섯 개 이상 달지 않는다. 다 달면 검색이 전부 걸려 소용없어진다
- `kw:` 는 **한 낱말**로 쓴다. "배당 잘 나오는" 같은 구절은 `kw:배당` 으로 줄인다

### 검색 함수

- `app/repositories/bbl.py`
- **시점 규약 대상이 아니다.** 가드 대상 세 표가 아니고, 블록은 시점 자산이 아니다
- 서명은 태그 목록과 블록 종류를 받아 블록 목록을 돌려주는 모양

받은 뒤 한 번 더 거른다.

**성향은 여기서 안 정한다.** "공격적으로" 라고 써 있어도 성향은 설문으로 확정된 값을
쓴다. 그 말은 `keywords` 에 남아 블록을 고르는 데만 쓰인다 — 말 한마디로 자기 한도를
올릴 수 있으면 성향 판정이 의미가 없다.

**종목 이름 찾기에서 두 번 고쳤다**

- 정확 일치를 먼저 본다. "KODEX 200" 은 부분일치로 넷이 걸려서(200TR · 200IT TR ·
  200미국채혼합50) **멀쩡한 요청이 "못 찾았다" 로 떨어졌다**
- 띄어쓰기와 대소문자를 무시한다. 사람이 종목명을 정확히 띄어 쓰지 않는다 —
  `kodex200` 도 찾는다
- 정확히 맞는 게 없고 부분일치가 여럿이면 고르지 않는다("국고채" 처럼).
  엉뚱한 종목을 담는 것보다 되묻는 편이 낫다 → 6단계 되묻기 입력이 된다

**실제 Ollama 로 확인한 것**

```
"반도체 위주로 공격적으로 굴리고 매달 정리해줘"
  → keywords=('공격적',) sectors=('SECTOR_SEMICONDUCTOR',)
  → 태그 ('kw:공격적','sector:semiconductor') → 블록 FL_HIGH_RISK_ONLY
  → 후보 3종목 (KODEX 반도체 · TIGER 반도체 · TIGER 미국필라델피아반도체나스닥)
  → 스키마 종목 선택지 3
```

- **"매달" 을 못 잡았다.** `kw:매달` 이 사전에 있는데 모델이 안 골랐다.
  프롬프트를 다듬을 일이지 버그는 아니다 — 5단계에서 같이 손본다

## 5단계 — 전략서 생성과 후처리

- **하는 일** (`m1-todo` §8 §9)
  - 컴파일 프롬프트 설계 (의도 + 블록 + 후보 종목 + 제약)
  - LLM 호출 — 동적 스키마를 넘겨 형식을 강제
  - 결과 파싱 → 허용범위로 접기 → 원출력과 조정 여부 보존 → 저장
- **주의**
  - **Ollama 는 형식 강제가 약해 스키마 위반이 실제로 난다.** 로컬 개발은 전부 Ollama 이므로 파싱이 유일한 방어선
  - 정식 실측은 **vLLM 쪽에서** 해야 함(기준 문서 지시). GPU 있는 팀원 협조 필요 — **10월**
  - **하드캡 클램프는 M1 이 하지 않음** (선행 안건 ② 확정). Validator 몫
    - M1 은 프리셋을 스키마에 박아 **애초에 못 어기게** 하는 데까지
    - 저장할 때 원출력과 확정값이 같고 `was_adjusted=false` 로 들어감
    - Validator 가 나중에 접고 `was_adjusted` 를 갱신
  - 저장 상태는 `draft` 까지만. 승인 상태가 되면 수정이 물리적으로 막힘
- **완료 기준**
  - 전략서가 형식 검사를 통과하고 데이터베이스에 저장됨
  - LLM 이 후보 밖 종목이나 범위 밖 비중을 내면 **파싱에서 걸림**
  - 같은 전략서를 M4 백테스트가 읽어서 돌릴 수 있음
- **남은 구멍**: Validator 본체가 없어서 **하드캡이 아무 데서도 안 걸림.**
  데모까지 안 나오면 하드캡을 넘는 전략서가 그대로 저장됨

### 결과 ✔ 2026-09-20

- `app/m1/postprocess.py` — 파싱·검사
- `app/m1/compiler.py` — 순서 잇기 (의도 → 블록 → 후보 → 스키마 → 프롬프트 → LLM → 파싱 → 저장)
- `app/repositories/specs.py` — 전략서 저장

**프롬프트는 "고르게 하는 것" 만 한다.** 무엇을 쓸 수 있는지는 스키마가 이미 막고
있다. 스키마가 강제하는 것을 말로 또 시키면 길어지기만 하고 지켜지지도 않는다.
프롬프트에 적는 것은 **스키마로 표현할 수 없는 것**뿐이다 — 하한 합계, 현금 남기기,
한 종목에 몰지 말 것.

**거절된 종목도 프롬프트에 넣는다.** "이건 못 담는다" 를 사유와 함께 알려 줘야
모델이 대신 다른 것을 고른다. 빼고 주면 왜 없는지 모른 채 비슷한 것을 또 찾는다.

**후처리가 보는 것은 스키마가 못 막는 것뿐이다**

- 하한이 상한보다 크지 않은가 (칸끼리의 관계라 JSON Schema 로 못 막는다)
- 하한의 합과 최소 현금이 1 을 넘지 않는가 — 넘으면 어떤 비중을 골라도 실행 불가
- 같은 종목이 두 번 들어오지 않았는가

후보 밖 종목과 범위 이탈도 **다시** 본다. 스키마가 막았을 텐데 또 보는 이유는
Ollama 의 형식 강제가 약해서다. 로컬 개발이 전부 Ollama 이므로 여기가 유일한 방어선이다.

**식별 정보는 모델이 정하게 두지 않는다.** 사용자 번호를 지어내면 남의 전략서가 되고,
전략서 번호가 겹치면 저장이 깨진다. 받은 값을 버리고 우리가 채운다.

**저장은 `draft` 까지.** 원출력과 확정값이 같고 `was_adjusted=false` 다 —
스키마가 이미 범위를 강제했으므로 M1 이 접을 것이 없다. 하드캡으로 접는 일은
Validator 몫이고 그때 이 둘이 갈라진다.

**실제 Ollama 로 확인**

```
"안전하게 채권 위주로 굴리고 매달 정리해줘"  (위험중립형)
  → 안전채권 포트폴리오
     114260 KODEX 국고채3년      0.10~0.50
     136340 RISE 중기우량회사채   0.10~0.50
     148070 KIWOOM 국고채10년    0.10~0.50
     153130 KODEX 단기채권       0.10~0.50
     157450 TIGER 단기통안채      0.10~0.50
     리밸런싱 calendar/monthly, 지표 vol_20
```

- 다섯 종목을 범위 안에서 골랐고 검사를 모두 통과했다.
  **복잡한 스키마(종목마다 선택지를 두는 형태)를 Ollama 가 지켜 냈다**
- 정식 실측은 여전히 vLLM 에서 해야 한다(기준 문서 지시) — 10월

**⚠ 컴파일 한 번에 2분이 넘는다 (2026-09-20 실측, qwen3:8b)**

종목마다 선택지를 둔 스키마라 제약 디코딩이 느리다. 여기서 두 가지가 걸렸다.

- `LLM_REQUEST_TIMEOUT_SECONDS` 기본값 120초로는 **읽기 시간초과로 죽는다.**
  `.env` 에 300초를 넣고 `.env.example` 에도 이유와 함께 적어 뒀다
- **진행 상황 스트림이 60초에 닫혔다.** 3초짜리 더미 태스크에 맞춘 상한(200회 × 0.3초)
  이라, 실제 컴파일은 완료보다 스트림이 먼저 끊긴다.
  10분으로 올리고 왜 그 값인지 주석에 남겼다 (`app/routers/jobs.py`)
- **이건 6단계에서 터질 자리였다.** 스트림을 붙이기 전에 미리 잡았다
- 속도 자체는 vLLM 으로 옮기면 나아질 가능성이 크다. 그래도 **데모에서 2분을 기다리는
  화면**은 설계에 반영해야 한다 — 진행 상황을 단계별로 흘려 보내는 이유가 여기 있다


## 6단계 — 파이프라인과 되묻기

- **하는 일** (`m1-todo` §10 §4)
  - 상태 머신 정의, 노드 연결, 되묻기 루프
  - `compile_spec` 작업의 속을 갈아끼움
- **격리 방침**
  - **닿는 접점은 한 군데.** 지금 3초 대기 후 끝나는 더미의 본체만 바꾼다
  - `app/m1/` 한 곳에 몰고 의존을 단방향으로 고정. 기존 모듈이 이쪽을 import 하지 않음
  - **작업 이름 `compile_spec` 은 바꾸지 않는다.** 라우터와 프론트가 이 이름에 붙어 있음
- **대화 상태는 Redis** (선행 안건 ③ 확정)
  - 메모리는 안 됨 — 컴파일은 `worker` 에서 돌고 사용자 응답은 `api` 로 들어옴.
    프로세스가 달라 파이썬 변수를 공유할 수 없음
  - 표를 추가하지 않으므로 전원이 데이터베이스를 날릴 일이 없음
  - 만료를 걸어 버려진 대화가 쌓이지 않게 함
- **의존성은 `m1` 묶음** (선행 안건 ④ 확정)
  - 이미지 분리는 아님. Dockerfile 하나를 세 서비스가 공유
  - 얻는 것은 "안 깔고도 앱이 뜬다" 와 "CI 에서 마커로 뺄 수 있다"
- **완료 기준**
  - Swagger 에서 요청 → 작업 번호 → 진행 상황 스트림으로 완료와 결과를 받음
  - 정보가 모자라면 되물어서 답을 받아 이어감
- **선행 안건 ② ④ 가 먼저**

**되묻고 나면 처음부터 다시 돈다.** 중간 상태를 되살려 이어가지 않는다. 사용자의 답을
처음 요청 뒤에 이어 붙이고 1번부터 다시 돈다. 단순하고, 사용자가 앞 내용을 뒤집는
답을 해도("역시 채권 말고 주식으로") 그대로 반영된다. 비용은 의도 추출 한 번을 더
부르는 것뿐이다.

**질문은 LLM 이 만들지 않는다.** 되물어야 하는 상황은 셋뿐이고 전부 우리가 아는
사실에서 나온다. LLM 에게 다시 설명해 질문을 받아 오면 느려지고(한 번에 수십 초),
매번 문구가 달라지고, 있지도 않은 선택지를 지어낼 수 있다. **실제 후보를 그대로
보여 준다** — "'국고채' 로 찾으면 여러 개가 나옵니다" + 목록.

**같은 질문을 두 번 묻지 않는다.** 답을 받고도 같은 것이 모호하면 무한히 되묻게 된다.
담을 게 없는 경우도 한 번만 묻고, 두 번째에는 사유를 그대로 올린다.

**상태 머신 라이브러리는 아직 안 넣었다.** 흐름이 한 줄이고 되돌아오는 자리가 하나라
함수 여섯 개로 충분했다. 단계를 함수로 갈라 뒀으니 LangGraph 로 감싸는 것은 얇은
껍데기 하나다 — 필요하면 그때 넣는다(선행 안건 ④ 는 "넣는다면 M1 전용 묶음" 이라는
결정이고, 지금 넣어야 한다는 뜻은 아니었다).

### 스키마를 다시 짰다 — 속도 때문에

처음엔 **종목마다 선택지를 하나씩** 뒀다. 종목코드와 이름이 고정값이라 지어낼 수
없는 형태였고 5종목일 때는 2분에 끝났다. 그런데 기본값인 10종목으로 돌리니
**300초 시간초과로 죽었다.** 제약 디코딩이 선택지 수에 급격히 느려진다.

**허용 범위가 같은 종목끼리 묶었다.** 범위는 위험등급마다 정해지므로 후보가 몇 개든
선택지는 **많아야 여섯 개(G1~G6)** 다.

```
전  {ticker: {const: "091160"}, name: {const: "KODEX 반도체"}, ...}   × 후보 수
후  {ticker: {enum: [...같은 범위의 종목들...]}, name: {type: string}, ...}   × 등급 수
```

**종목명은 스키마에서 뺐다.** 종목코드만 정해지면 이름은 우리가 아는 값이라,
받아 놓고 후처리에서 덮어쓴다. 모델에게 정확한 문자열을 받아 내려고 문법을 키울
이유가 없다.

바꾼 뒤 10종목으로 다시 돌리니 **통과했다. 다만 5분 7초** 걸렸다(의도 추출 + 생성).
죽지는 않지만 데모에서 기다릴 수 있는 시간은 아니다. 줄일 수 있는 곳은 셋이다.

- 후보 수(`DEFAULT_TARGET`) — 프롬프트와 출력이 같이 짧아진다
- vLLM 으로 옮기기 — 제약 디코딩 구현이 다르다. 10월 실측 때 같이 잰다
- 의도 추출과 생성을 한 번으로 합치기 — 정확도를 잃을 수 있어 마지막 수단

### 겪은 것

- **worker 컨테이너는 `--reload` 가 없다.** 태스크 본체를 바꿨는데 옛 코드가 계속
  돌아 테스트가 엉뚱하게 통과했다. `docker compose restart worker` 가 필요하다
- 그 전까지 진행 상황 스트림 테스트는 **더미 태스크가 `completed` 를 돌려주는 것**에
  기대고 있었다. 지금은 성향 없는 사용자로 도는 `failed` 를 본다 — 스트림 패턴이
  동작하는지가 요점이고 컴파일 결과는 다른 파일이 본다
