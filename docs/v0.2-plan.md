## 1. 방향 (2026-11-02 결정)

- demo/ 를 그대로 키우지 않고 메인 구조로 옮긴다(B안). backend/app 에 구현하고, DB 의 종목 원장과 가격 스냅샷을 쓰고, 화면은 Next.js 로 만든다
- v0.1 은 한 번에 지우지 않는다. v0.2 를 새 파일로 만들고 모듈을 하나씩 옮긴 뒤, 마지막 단계에서 v0.1 과 쓰지 않게 된 코드를 지운다. 단계마다 남은 기능이 돌아야 한다
- 데모 범위: 이름으로 말한 개별주와 ETF, 그 종목 자신의 지표만. 업종 고르기, 지수 · VIX 주체, 배당, 대화 · 버전 테이블은 뺀다

## 2. 단계

- 각 단계는 사용자가 지시할 때만 시작한다. 단계마다 브랜치를 따고 main 으로 PR 한다

### 1단계 — 전략서 v0.2 계약

- `backend/app/contracts/strategy_v0_2.py`: 설계 문서 "전략서와 AI 출력의 모양" 의 전략서 v0.2 를 Pydantic 으로 쓴다
- 모양은 평가 데이터셋 정답(`eval/dataset.jsonl` 의 expected_spec)과 같고 meta 칸을 더한다
- 계약은 모양만 본다(타입, 허용 값, 필수 칸). 기간 허용 목록, 단위, 손절을 살 때 쓴 것 같은 뜻 검사는 검사 3단계 몫이다
- 끝난 기준: 평가 데이터셋 개발용(dev) ok 문장의 정답 전략서가 모두 계약을 통과한다. 최종 평가용(test)은 열지 않는다
- 1단계 결과 (2026-11-02)
  - `backend/app/contracts/strategy_v0_2.py` 와 테스트 `backend/tests/test_strategy_v0_2.py`(28건)
  - dev ok 20건의 정답 전략서가 모두 통과한다
  - 종목코드는 숫자로 시작하는 6자리로 받는다. 대문자 6자만 보면 NASDAQ 같은 말이 종목코드로 통과했다. 원장 3,850종목이 모두 이 형식이다
  - 업종 고르기(selector)는 데모 범위 밖이지만 정답 전략서에 있어 모양은 받는다. 고른 종목은 resolved_tickers 에 둔다
  - 아직 아무 모듈도 v0.2 를 쓰지 않는다. v0.1 흐름은 그대로 돈다

### 2단계 — 조건형 백테스트

- 설계 문서 "데모 범위와 조건형 백테스트" 의 규칙 8개
- 가격은 `app/repositories/price_daily.py` 로 as_of 를 지켜 읽는다. 주식 · ETF 구분은 `instruments.kind`
- demo/core 의 지표 · 세금 · 체결 코드를 참고하되, 거래정지일은 행을 지우지 않고 주문을 미룬다. 비교 기준은 같은 종목 보유와 KODEX 200 보유
- 끝난 기준: 대표 예시 전략서(삼성전자 RSI 30 · 5일선)가 돈다. 같은 입력 2회 결과 동일. 룩어헤드 테스트(지표 표의 t일 값과 t일까지 자른 계산 값이 같음) 통과
- 2단계 결과 (2026-11-02)
  - `app/backtest/signals.py`(지표 시계열), `taxes.py`(세율과 세금 구분), `rules_engine.py`(체결 · 평가 엔진과 비교 기준), `rules_service.py`(DB 가격 · 종목 원장으로 실행)
  - 엔진은 features.py 처럼 stdlib 만 쓰는 순수 함수다. 그래서 룩어헤드 테스트가 pandas 없이 매번 돈다
  - 대표 예시: 기본 기간(2023-01-01 ~ 2025-12-31)에 체결 8건, 거래 4건, 0.6초. 두 번 돌려 결과가 같다. demo/ 의 결과와 거래 수가 같다
  - 테스트: 지표 21건(잘라서 계산한 값과 같음, 미래를 바꿔도 과거 값이 같음, features.py 와 같은 정의), 엔진 14건(체결 시점과 비용, 팔기 우선, 거래정지일 미룸, 마지막 날 신호, 보유 일수, 손절, 자리 크기와 상한, 세금 셋, 미래 가격을 바꿔도 과거 체결이 같음, 재현성), DB 2건(requires_backfill)
  - 새로 정한 정의(설계 문서에 적음): 수익률과 변동성은 소수, 거래량 비율은 오늘을 뺀 직전 20일 평균과 비교, 2021 · 2022년 주식 거래세 0.23%
  - 미루는 동안 반대 주문이 생기면 둘 다 취소한다는 규칙은 넣지 않았다. 한 번 사면 팔 때까지 더 사지 않으므로 그런 경우가 생기지 않는다
  - 하지 않은 것: 자산 배분형(rules 가 빈 v0.2) 실행. 지금은 v0.1 러너(runner.py)가 돌린다. v0.1 을 지우기 전에 v0.2 로 옮겨야 한다(9단계 전)

### 3단계 — 표현 표와 조각 찾기

- `db/seeds/expressions.yaml`(표현 표와 거절 사전)과 조각 찾기 규칙
- 첫 내용은 eval/GUIDE.md 표현 표, 동사 표, dev 문장에서 채운다
- 끝난 기준: dev 문장에서 의미 있는 낱말 중 조각으로 잡힌 비율을 잰다(설계 문서 "확정 전에 잴 것" 1)

### 4단계 — AI 짝짓기와 근거 검사

- 조각 종류로 좁힌 스키마, 프롬프트, 재시도 1회, 안 쓰인 조각 검사
- 끝난 기준: dev 문장에서 조각 번호 방식과 근거 글자 방식을 비교한다(설계 문서 "확정 전에 잴 것" 2)

### 5단계 — 값 바꾸기, 판정, 전략서 조립, 저장

- 상태 계산, 기본값, 부분 조립, 되묻는 순서, 질문과 선택지, 답 처리, 세션
- 저장 방식 (2026-11-02 결정, A안): strategies 에 spec JSONB 칸을 마이그레이션으로 더해 v0.2 전략서를 통째로 저장한다. 지금 strategies 는 rebalance · signal_rules · constraint_user 칸과 strategy_assets 로 쪼개 저장해서 rules · backtest · meta 를 둘 자리가 없다. 옛 칸은 v0.1 을 지울 때(9단계) 정리한다

### 6단계 — 검사 1~4단계

- v0.2 용 모양 · 존재 · 말이 되는지 · 근거 검사. 결과는 validation_logs(stage 1~4, violations 항목의 종류 block · ask · warn)

### 7단계 — 설명 틀과 API

- "AI가 이해한 전략" 설명, 판정 결과 응답(ok · ask · reject), 답 보내기, 백테스트 실행

### 8단계 — 화면

- 입력, 되묻기, 전략서 확인, 백테스트 결과. Next.js

### 9단계 — 평가와 정리

- dev 문장으로 변환 정확도와 판정 성능을 잰다. 비교 대상(LLM 코드 직접 생성)은 demo/baseline 을 옮긴다
- v0.1 계약과 쓰지 않게 된 코드, demo/ 정리
