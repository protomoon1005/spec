## 2. 비중 체인 합류

`810665a`(M2 담당)는 PR #27 로 `feat/m2-validator` 에만 들어가고 main 에 합류하지 못했다. 그 사이 PR #31(`c1f2501`)이
"백테스트가 검증 확정값을 쓴다"를 다른 방식으로 구현해 6파일이 충돌했다. RiskSizer v0.1 상수와 근거(docs/m2-algorithms.md 2장 소절)는
M2 담당의 2026-10-04 결정이라 그대로 들여왔다.

### D1. 확정값 출처 · 실패 정책 — **C(혼합) 선택**

| B | `c1f2501` 방식 + 체인 — 기록 통과면 확정값, 아니면 `_raw` + 성향 기본 현금을 **체인에 넣음** |

차단으로 바꾸려면 `m2_chain.FALLBACK_WHEN_BLOCKED = False` 한 줄(테스트 있음).

**탈락** — A: 팀 결정(차단)을 코드로 선점, 프론트 칸 깨짐. B: 미검증 값이 통제 계층에 들어가 불변식이 깨지고, 폴백용 1회 손실 한도를 새로 정해야 함.
B': 기록 없는 draft 가 체인을 전혀 타지 않고, 그 경로는 현금 · weight_min 을 못 지킨다.

## 3. 전략서 승인 API

### D1. API 모양 — **`POST /specs/{spec_id}/approve {run_id, user_comment?}` → 201 포트폴리오**

| 후보 | 요청 수 | 이탈 · 반복 뒤 |
|---|---|---|
| (a) `POST /portfolios`(대기) → `POST /portfolios/{id}/approve` | 2 | 1단계 두 번 누르고 이탈하면 **대기 포트폴리오 2행** |
| (b) `POST /portfolios {spec_id, run_id}` | 1 | 두 번째 409, 포트폴리오 1 |
| (c) `POST /specs/{spec_id}/approve` (채택) | 1 | 두 번째 409, 포트폴리오 1 |

(b)와 (c)는 측정이 같다. 승인은 전략서에 대한 결정이고(`approvals.spec_id`, 전제조건이 전부 전략서 쪽), `POST /specs/{id}/validate` 와 같은
모양이며, 나중에 "거절"을 같은 자리에 둘 수 있어 (c). 501 자리표시 `POST /portfolios/{id}/approve` 는 승인 전에는 번호가 없어
원래 부를 수 없는 주소라 없앴다.

### D2. 전제조건 · 상태 코드

| 순서 | 조건 | 실패 |
|---|---|---|
| 1 | 내 전략서 (admin 도 남의 것은 안 됨) | 404 |
| 2 | draft | 409 |
| 3 | 마지막 검증이 4단 모두 통과 | 409 |
| 4 | run_id 가 내 실행 | 404 |
| 5 | 그 실행이 이 전략서의 것 | 422 |
| 6 | 끝난(done) 실행 | 409 |
| 7 | 그 실행이 **지금 확정값으로 M2 체인을 돈 것** | 409 |

7번의 "신선도" 판정 후보를 실제 검증기 · 러너로 만든 시나리오 7개에 대 보았다.

| 후보 | 탈락 · 채택 이유 |
|---|---|
| R1 실행 없어도 됨 | 실행 없음 · 실패한 실행 · 남의 전략서 실행을 받는다 |
| R2 실행 필수 + 같은 전략서 + done | 검증 전(AI 원래 범위)으로 돈 실행을 받는다 |
| R3 R2 + `validation.status == passed` | 체인 형식에서 정상 실행을 거른다 |
| R4 R2 + 실행 시각 ≥ 검증 시각 | 결과가 같은 재검증 한 번에 3분짜리 백테스트를 다시 돌리게 한다 |
| R5 R2 + 결과의 종목별 확정 범위 == 지금 `spec_universe` | 승인 작업 단독으로는 7개 모두 바라는 답 |
| **R6 R2 + 결과의 체인 입력(`window_results.m2`) == 지금 확정값** (채택) | 아래 |

R5 는 두 작업을 합친 뒤 구멍이 생겼다. 체인 합류로 기록 없는 draft 도 메모리 재검증 확정값으로 돌게 되자, 범위만 비교하면
현금 목표 · 1회 손실 한도 · 최소 간격이 다른 실행을 놓친다. 그래서 "지금 확정값"을 백테스트와 같은 함수(`m2_chain.recorded_policy`)가
내고, 실행이 실제로 쓴 체인 입력과 `same_policy` 로 대조한다(범위 · 현금 목표 · 1회 손실 · 최소 간격 · 하드캡 버전, 출처는 보지 않음).
막혀서 기본 경로로 돈 실행(`m2` 없음)은 409. 끝까지 흐름 테스트로 확인했다: 기록 전 실행(revalidated)과 기록 후 실행(recorded)의
체인 입력이 같아 기록 전 실행도 근거가 되고, 승인 뒤 백테스트(stored)는 승인 전 실행과 곡선 · 주문이 같다.

run_id 는 필수다. `approvals.run_id` 는 NULL 허용이지만 "무엇을 보고 승인했나"의 기준점이고, 최종 확인 화면이 백테스트 결과를 보여 준 뒤 승인한다.

### D3. 원자성 — **한 트랜잭션**

가중치 기록 단계에 예외를 주입해 네 표를 셌다.

| 후보 | 실패 뒤 상태 |
|---|---|
| T1 한 트랜잭션 (채택) | 승인 0 · 포트폴리오 0 · 가중치 0 · draft — 다시 누르면 정상 승인 |
| T2 순차 + 보상 | 보상(approved→draft)을 **Spec 불변 트리거가 거부** → 승인 · 활성 포트폴리오 · 가중치 없음이 영구히 남음 |
| T3 Celery 뒤처리 | T2 와 같은 상태, 실제 워커면 사용자는 201 을 봄 |

성공 경로 평균 T1 5.94 ms, T2 7.09 ms(20회). 연결은 `live.init_view_weights(..., conn=)` → `insert_view_weights(..., conn=)` 로 넘겨
가중치 SQL 은 여전히 `app/repositories/` 에만 있다.

### D4. 동시성 — **전략서 행 `SELECT … FOR UPDATE`**

같은 전략서에 8스레드 동시 승인 × 5회(40요청).

| 후보 | 결과 |
|---|---|
| 잠금 없음 | 포트폴리오는 회당 1개지만 **트리거 예외 35/40(사용자에게 500)** — 트리거 부수효과에 기대는 구조 |
| FOR UPDATE (채택) | 성공 5 · 409 35 |
| advisory lock | 같음. 단 `record_validation` · `delete_draft_spec` 의 행 잠금과 직렬화되지 않음 |
| 조건부 UPDATE | 같음, 가장 빠름(28.7 ms vs 39.8 ms). 상태를 먼저 바꾸고 전제조건을 뒤에 보는 순서가 되고 404/409 구분에 SELECT 가 더 필요 |

유일 인덱스는 스키마 판단이라 하지 않았다(아래).

### D5. FN-409 as_of — **활성화 시각의 KST 날짜**

`daily_judge` · `update_view_weights` 를 후보별로 실제로 돌렸다. 판단에 들어가는 가중치는 어느 후보든 1/3 로 같다
(당일은 strict `<` 로 대체값 1/3). D-1 은 포트폴리오가 생기기 전 날짜의 행이 되어 감사 기록이 거짓이 되고, D+1 은 첫 정규 갱신일과 충돌한다.
DB 세션 시간대가 UTC 라 KST 00:30 에 승인하면 UTC 날짜가 하루 어긋나는 것을 확인해, `activated_at` 과 같은 `now()` 에서
`AT TIME ZONE 'Asia/Seoul'` 로 날짜를 낸다.

### D6. 값

| 칸 | 선택 | 탈락 |
|---|---|---|
| `portfolios.status` | `active` | `running`(전략서 status 와 같은 낱말이 다른 뜻), `pending`(D1 에서 대기 단계를 버림) |
| `initial_cash` | 승인 근거 실행의 seed_money(지금 10,000,000) | 요청값(화면에 입력 없음, 백테스트와 다르면 비교가 깨짐) |
| `mode` | `virtual`, account_no NULL | `paper`(모의계좌 연동은 12월 이후) |

전략서는 `approved` 에 머물고 "운용 중"은 `portfolios.status` 로 본다. `draft → running` 직행은 트리거가 `approved` 만 막아 Spec 불변이 깨지므로 쓰지 않았다.
