### 전략서와 승인

- **승인한 전략서의 상태를 바꿀 수 없음**
  - 승인 뒤에는 고치지 못하게 데이터베이스가 막아 놨음
  - 그 잠금이 "상태" 칸까지 얼려서 `승인 → 운용중 → 종료` 로 넘어가는 것 자체가 안 됨
  - 얼려야 할 건 종목과 비중이지 상태는 아닐 가능성이 크지만, **팀 확정 전이라 코드를 안 바꿈**
  - 우회 (2026-10-20 승인 API) — 승인한 전략서는 `approved` 에 머물고, "운용 중"은
    `portfolios.status = 'active'` 로 본다. `draft → running` 으로 바로 보내는 길은 쓰지 않았다 —
    트리거가 `approved` 만 막으므로 `running` 전략서는 다시 고칠 수 있게 되어 Spec 불변이 깨진다
  - 같은 이유로 승인을 되돌리는(approved → draft) 보상 처리가 불가능하다. 승인 흐름은 한 트랜잭션이다

- **승인 · 포트폴리오 표의 스키마 판단이 남아 있음** (2026-10-20 기록, 2026-10-21 중복 승인 인덱스는 해결)
  - `approvals` ↔ `portfolios` 를 잇는 칸이 없다. ERD 는 1:1(APPROVALS activates PORTFOLIOS)인데
    `spec_id` 로만 이어진다. 전략서가 draft→approved 를 한 번만 거치므로 지금은 하나로 정해진다
  - (해결 2026-10-21) 중복 승인 — 전략서 행 `SELECT … FOR UPDATE` + draft 확인에 더해 DB 부분 유일 인덱스
    `uq_approvals_spec_approved ON approvals (spec_id) WHERE approved` 를 둔다(`db/migrate/002`). 거절 기록은 여러 번 가능.
    `portfolios (spec_id)` 에는 걸지 않았다 — 같은 전략서로 포트폴리오를 다시 여는 기능을 막지 않으려고
  - `portfolios.status` 에 CHECK 가 없다. 코드 상수는 `active` 하나(`app/repositories/portfolios.py`).
    정지 · 종료 값을 정할 때 CHECK 를 둘지 함께 정한다

- **가입으로는 일반 사용자만 만들어짐**
  - `POST /auth/signup` 은 권한을 항상 `retail` 로 고정함. 요청으로 고를 수 없음
  - `pro`·`admin` 으로 올리는 경로가 없어서 데이터베이스에 직접 넣어야 함
  - 이메일 인증도 없음. 메일 발송 경로가 없고 모의투자라 프로토타입 기준으로 생략함

- **501 로 비어 있는 API 들의 응답 형식은 바뀔 수 있음**
  - 2026-10-20 승인은 `POST /specs/{spec_id}/approve`, 포트폴리오 보기는 `GET /portfolios/{id}` 로
    채웠다. 자리표시였던 `POST /portfolios/{id}/approve` 는 없앴다(승인 전에는 포트폴리오 번호가 없다)
  - 지금은 표의 확정 칸만으로 모양을 보여주는 최소한
  - 페이징·부분 수정·오류 형식 같은 건 각자 만들 때 정함
  - **전략서(Spec) 형식만은 예외.** 전원 합의가 필요한 고정 계약

- **백테스트 결과는 `backtest_metrics.window_results` 에 담는다**
  - 자산곡선·결정 목록·실패 이유는 칸이 없어서다. 칸 이름(워크포워드 창별 결과)과 뜻이 어긋난다 (2026-09-28 결정 D2-a)
  - 확정값이 있는 실행의 비중은 M2 체인(`app/m2/weights.py`, `app/backtest/m2_chain.py`)이 낸다(2026-10-04 구현, 2026-10-20 main 합류).
    그룹캡 적용 내역도 `group_cap_applications` 표가 아니라 여기 `decisions[].m2` 에 있다 — 표는 `decision_id` 가 필요한데
    백테스트 결정은 DB 행이 아니다. decision_records 연결은 데모 후
  - `window_results.m2`(체인 입력: 범위·출처·1회 손실·간격·RiskSizer 상수)는 2026-10-21 부터 `GET /backtest/runs/{id}` 의
    `m2` 로 나간다(리포트가 범위를 읽는다). `decisions[].m2` 는 결정 목록에 섞여 나간다

- **백테스트가 Validator 결과를 쓰는 방식** (2026-10-04 확인 → 810665a · c1f2501 를 2026-10-20 합침. 남은 것만)
  - `service.run_spec_backtest` 경로만 해당한다. `scripts/run_backtest_vbt.py`·TS 대조는 두 러너 일치를 보려고
    지금도 `_raw` + `policy.resolve_bounds` + `policy.CASH_MIN` 을 쓴다
  - 확정값 출처는 `app/backtest/m2_chain.resolve_policy` 한 곳이다. 실행 기록 `validation` 의 `status`·`source` 로 남는다
    - approved 이후 — 마지막 검증 기록 + spec_universe 확정 범위(`stored`). 통과 기록이 없으면 실패
    - draft, 기록 있음 — 마지막 검증이 4단 통과면 그 값(`recorded`)
    - draft, 기록 없음 — Validator 를 메모리에서 다시 돌린다(`revalidated`, 기록 안 함). 실측 0.06~0.36초
    - 막힘(기록 또는 재검증) — 백테스트가 실패한다. 아래
  - **검증에서 막힌 전략서는 백테스트하지 않는다** (2026-10-21 사용자 결정. 원래 c1f2501 이 "팀 결정"으로 남긴 항목이라
    팀 공유 필요) — 실패 이유 "검증 N단에서 막힌 전략서는 백테스트하지 않는다 …" 로 끝나고, 백테스트 화면이 하드캡 화면으로
    안내한다. 예전처럼 러너 기본 경로(AI 원래 범위, RiskSizer 없음)로 돌리려면 `m2_chain.FALLBACK_WHEN_BLOCKED = True` 한 줄이다.
    그 전에 돈 실행에는 "AI 원래 범위" 배지가 그대로 보인다
    - 막힌 전략서의 `_raw` 를 M2 체인에 넣지 않는 이유: 1장 불변식(Σweight_min ≤ 1 − cash)은 Validator 가 보장하는 것이라
      `_raw` + 성향 기본 현금으로는 깨진다. M1 은 전략서 자신의 `cash_min` 으로만 검사하므로, LLM 이 성향 기본값보다 낮은
      현금을 쓰면 통과한다 — 무작위 5000건 중 20건, 성향 1·현금 0.05·하한 합 0.90 픽스처에서 체인이 거부
  - **승인은 M2 체인을 돌지 않은 실행을 근거로 받지 않는다**(409 — 예전 폴백 실행 포함). 승인 근거 실행은 M2 체인을 돌았고
    그 입력(`window_results.m2`: 범위 · 현금 목표 · 1회 손실 · 최소 간격 · 하드캡 버전)이 마지막 검증 기록의 확정값과
    같아야 한다(`m2_chain.recorded_policy` · `same_policy`, 2026-10-20). 출처는 보지 않으므로 기록 전 메모리 재검증으로
    돈 실행도 값이 같으면 근거가 된다. approved 경로(`stored`)는 승인 → 백테스트로 이어 돌고, 결과가 승인 전 실행과
    같다(`tests/test_portfolio_approve.py` 끝까지 흐름 테스트)
  - 메모리 재검증의 기준일은 백테스트 구간 끝이고, 검증 API(`POST /specs/{id}/validate`)는 가격 표의 마지막 거래일이다.
    실전략서 2건 × 기준일 6개에서 결과가 같았지만 구간을 짧게 잡으면 2단(가격 대조)·3단(낙폭) 판정이 갈릴 수 있다
  - draft 의 기록된 검증은 활성 하드캡이 바뀌어도 다시 계산하지 않는다(지금은 하드캡 버전이 하나뿐이라 해당 없음)

    메모리 재검증은 활성 버전을 적는다. 하드캡이 둘 이상이 되면 표기가 실제와 다를 수 있다(값은 맞다).
    승인 대조(`same_policy`)는 표기를 보지 않고 하드캡이 바꾼 값만 본다. 칸 추가는 스키마 판단
  - **확정 범위가 DB 를 거치면 끝자리가 잘린다** (2026-10-21 리뷰) — 0.2857142857142857 → 0.285714285714286(차 2.8e-16).
    범위 보정이 긴 소수를 만들면 메모리 재검증 실행과 기록 · 승인 뒤 실행이 마지막 자리에서 갈릴 수 있다.
    승인 대조는 1e-9 허용 오차라 영향이 없다. 지금 픽스처(0.0 · 0.3 류)에서는 결과 차이가 재현되지 않았다
  - 낙폭 상한(`max_drawdown`)은 체인에서 쓰지 않는다. 운용 중 낙폭 통제는 데모 범위 밖
  - **리포트 화면의 범위는 실행이 쓴 확정값을 그린다** (2026-10-21) — `frontend/lib/data.ts` 가 `m2.bounds` 가 있으면 그 값을,

  - 주문은 비중 단위다. 수량 환산·단수 잔여 처리는 vectorbt 가상 체결이 대신한다 — 실운용 연결 때 정한다
  - **백테스트 결정 기록의 주문(`decisions[].m2.orders`)은 직전 목표 비중 대비 변화분이다** (2026-10-21 리뷰)
    - FN-504 는 "현재 비중과 목표 비중의 차이"인데, 백테스트 체인은 리밸런싱 사이 가격으로 흘러간 비중을 모른다
      (vectorbt 가 목표 비중표를 받아 나중에 한꺼번에 체결한다). 그래서 두 리밸런싱의 목표가 같으면 기록된 주문은
      빈 목록이지만 실제로는 흘러간 만큼 되돌리는 거래가 일어난다
    - 실제 거래의 재현성은 이 기록이 아니라 곡선 · 목표 비중으로 확인한다(`test_portfolio_approve` 끝까지 흐름 ·
      requires_backtest 재현성 테스트). 실운용은 `positions.current_weight` 로 현재 비중을 받아야 한다 — 연결 때 정한다

- **가격 표에 종가가 고가·저가를 1~4원 벗어나는 행이 828건** (2026-10-04 확인)

### 뉴스와 AI 모델

- **뉴스 수집 파이프라인이 제거됐는데 표는 남아 있음**
  - 2026-09-19 `jun` 이 지움 (커밋 `ee08952`, 11개 파일 1,178줄)
  - `news_articles`·`news_sentiment` 표와 벡터 색인은 스키마에 그대로 있다
  - **감성 관점의 입력이 통째로 없는 상태.** 다시 만들 계획인지 확인 필요
  - 그동안 쌓인 기사도 같이 사라졌을 수 있다 — 지나간 날은 다시 못 받는다

- **뉴스 표에 원문을 담는 칸이 있지만 채우면 안 됨**
  - 상위 규칙이 "뉴스 원문은 저장하지 않는다, 메타정보·점수·태그만 저장한다"고 못 박음
  - 다시 만들 때 이 규칙을 지켜야 함

- **문장을 숫자로 바꾼 값의 크기를 768로 정해 둠**
  - 원래 설계 문서에 크기가 안 적혀 있었는데, 크기가 없으면 검색 색인을 만들 수 없어서 정함
  - **나중에 바꾸려면 칸 타입 변경 + 색인 재생성이라 되돌리는 비용이 큼.** 쓸 모델을 빨리 정할수록 좋음

- **GPU 쪽 AI 서버는 한 번도 안 돌려 봄**
  - 코드만 있고 실행한 적 없음. GPU 있는 팀원이 처음 검증해야 함
  - GPU 없는 쪽(Ollama)은 실제로 응답을 받아 확인함

### 3관점 판단 (2026-10-05 실물 스코어러 연결 후)

- **시장분석 모델 신호가 약함**
  - 보정 구간 accuracy 0.668 은 그 구간의 상승 기저율과 비슷하다
  - isotonic 이 넓은 구간을 한 계단으로 묶어 서로 다른 원확률(0.41·0.59)이 같은 보정확률로 접히기도 한다
  - 피처·하이퍼파라미터 개선은 데모 뒤 과제
- **`ml_models` 의 accuracy·brier 는 보정 구간 표본 안의 값이라 낙관적**
  - 피처셋 버전·표본 수를 둘 칸도 없어 artifact JSON 과 버전 문자열에만 있다. 컬럼 추가는 스키마 결정
- **백테스트 첫 실행이 3분 남짓**
  - 20거래일마다 재학습(확정 규칙)이라 3년 구간이면 모델 36개를 학습한다. 워커 프로세스가 cutoff 별로 캐시하므로 두 번째부터는 빠르다
  - `train_model` 로 미리 학습해 두면 MinIO 에서 읽는다
  - 가격을 다시 적재(정정)해도 이미 뜬 워커는 옛 캐시를 쓴다 — 재적재 뒤 워커 재시작
- **라이브 판단 기록이 같은 날 여러 번 쌓일 수 있음**
  - `decision_records` 에 (portfolio_id, as_of, mode) 유일 제약이 없다. 채점은 판단일마다 마지막 기록만 쓴다
  - 유일 인덱스를 둘지는 스키마 결정
- **백테스트 판단은 DB 에 안 남음** — `decision_records`·`view_weights` 의 run_id 축(Q3 마이그레이션) 대기. 지금은 `window_results.decisions[].views` 에만 있다
- **FN-409 초기 가중치는 활성화일(KST)로 남는다 — 그날의 가중치 갱신과 겹침** (2026-10-20 승인 API 에 연결)
  - 승인이 같은 트랜잭션에서 `live.init_view_weights` 를 부른다(`app/m2/approval.py`). as_of 는 활성화 시각의 KST 날짜
  - 활성화 당일 판단은 strict `<` 라 이 기록을 못 읽고 같은 값(1/3) 기본값을 쓴다. 다음 날부터 기록을 읽는다
  - **같은 날 `update_view_weights` 를 돌리면 유일 인덱스 충돌**(실측 UniqueViolation). 매일 갱신을 걸 때
    첫 갱신은 활성화 다음 날부터여야 한다. 그날은 채점할 판단도 없다
  - **판단 · 갱신을 가격 날짜(데이터 시계)로 돌리면 어긋남** — 지금 가격 끝은 2025-12-30 이고 활성화일은
    벽시계(2026-10-20)다. 2025 날짜로 갱신을 쌓으면 2026-10-21 이후 읽기에서 활성화일의 1/3 이 그 갱신을
    가린다(실측). 라이브 루프는 벽시계 하나로 돌려야 한다
- **시장온도 채권 종목 확률이 0.5 가 아님** — 국면 조건부 빈도라 "국면과 무관하게 대체로 올랐다"는 기저율이 그대로 나온다. 브리핑 화면에서 설명 필요
