## 1단계 · ETF 유니버스 60종목 (최우선)

### 1-1. 티커·종목명 자동 수집

```
scripts/build_etf_master.py 를 실행해서 db/seeds/04_etf_master.csv 를 채워라.

- pykrx 로 현재 상장된 ETF 의 티커·종목명·상장일을 가져온다
- 2023-01-02 시점 티커 목록과 오늘 목록을 비교해 그 사이 상장폐지된 종목을 찾는다
  최소 1건은 반드시 찾아서 delisted_date 와 active=false 로 CSV 에 넣는다
- 거래대금 기준 상위 60종목으로 추린다 (상장폐지 1건은 그와 별도로 포함)
- mdd_3y, volatility_1y 는 pykrx 시세로 계산 가능하면 채우고, 안 되면 비워둔다

risk_tag / group_id / sector / country 네 컬럼은 헤더만 만들고 값은 전부 비워둬라.
추정해서 채우지 마라. 사람이 판단할 부분이다.

CSV 는 UTF-8 with BOM 으로 저장해라 (엑셀에서 종목명이 깨지지 않게).
```

### 1-2. 사람이 CSV 를 직접 채운다

엑셀로 열어 네 컬럼을 채운다. 판단이 필요한 건 `risk_tag` 뿐.

| 등급 | 대상 |
|---|---|
| G1 | 레버리지·인버스 (2배, -1배 등) |
| G2 | 단일 섹터 주식형, 신흥국 |
| G3 | 시장대표 주식형 (KODEX 200, TIGER 코스닥150 등) |
| G4 | 혼합형, 배당주 |
| G5 | 중장기 국공채·회사채 |
| G6 | 단기채·MMF 성격 |

`group_id` 는 EQUITY / BOND / COMMODITY.
`sector` 는 반도체 · 2차전지 · 바이오와헬스케어 · 금융 · 인터넷과플랫폼 · 소비재 · 기타.
`country` 는 한국 · 미국 · 기타.

### 1-3. 적재와 검증

```
db/seeds/04_etf_master.csv 를 etf_master 테이블에 적재하는 걸 tasks.ps1 seed 에 연결해라.

적재 후 다음을 검증하는 단계도 넣어라.
- 60행 이상 적재됐는지
- group_id FK 위반이 없는지 (빈 값이 있으면 그 종목을 목록으로 출력하고 실패시켜라)

- active=false 인 상장폐지 종목이 최소 1건 있는지

country 컬럼은 etf_master 스키마에 없다(알려진 설계 구멍 ③).
지금은 CSV 에만 두고 DB 적재에서는 제외해라. 스키마를 임의로 바꾸지 마라.

## 2단계 · 비중 산출 체인 (M4가 기다리는 부분)

**플랜 모드로 시작한다** (`Shift+Tab` 두 번).

```
docs/m2-algorithms.md 를 읽고 2장(신호→비중 매핑)과 3장(검산 예제)에 따라
RiskSizer / WeightMapper / GroupCapEnforcer / OrderBuilder 를 구현해라.

먼저 계획만 보여줘라. 특히 다음 두 가지에 답하고 멈춰라.
1. 0단계에서 확인한 M4 쪽 기존 코드와 어떻게 연결할 것인가.
   기존 코드를 대체하는가, 그 자리에 끼워넣는가.
2. RiskSizer 의 ATR 기반 상한 산출식. 문서에 "ATR 기반"까지만 있고
   구체적 계산식이 없다. 선택지를 제시하고 멈춰라. 임의로 정하지 마라.

승인 후 구현 순서는 반드시 아래를 지켜라.

[테스트 먼저]
docs/m2-algorithms.md 3장의 검산 예제를 회귀 테스트로 먼저 작성해라.
단계별 중간값을 각각 단언한다 — 선형매핑 직후, 정규화·클램프 후, 그룹캡 후.
소수점 넷째 자리까지 일치해야 한다. 현금 잔여 0.0757 과
그룹캡 축소 계수 0.95106 도 단언해라.
테스트가 먼저 실패하는 걸 보여준 다음 구현해라.

[실행 순서 고정]
RiskSizer → WeightMapper → GroupCapEnforcer → OrderBuilder 순서를 바꾸지 마라.
RiskSizer 상한은 Spec 의 weight_max 와 min 연산으로 결합된다.
이 순서가 바뀌면 거부 재시도 루프가 생긴다는 게 설계 근거다.

[그룹캡 2계층]
상위 자산군(성향별 상한)을 먼저, 하위 섹터 0.30·국가 0.50 을 나중에 적용한다.
각 계층의 적용 내역을 group_cap_applications 에 sum_before / cap / scale_factor 로
각각 기록해라. 축소 후에도 각 종목은 weight_min 이상을 유지해야 한다.

[하지 말 것]
Validator 본체(FN-301~305)는 3단계에서 한다. 여기서 손대지 마라.
```

구현이 끝나면 한 번 더:

```
검산 예제 외에 경계 케이스 테스트를 추가해라.
- 모든 신호가 -1 일 때 전 종목이 weight_min 에 놓이는가
- 모든 신호가 +1 일 때 상한과 그룹캡에 걸리는가
- 데드존(|s| < 0.10)이 0 으로 처리되는가
- 그룹캡 축소 후 weight_min 을 침범하지 않는가
- 현금 잔여가 항상 cash_min 이상인가
```

## 3단계 · Validator 4단 + 범위 자동 보정

```
docs/m2-algorithms.md 1장(범위 실행가능성 보정)과 6장(4단 Validator)에 따라
FN-301 ~ FN-308 을 구현해라.

[핵심 — FN-304 범위 자동 보정]
불변식과 case A/B 규칙은 1장에 그대로 있다. 그것만 따라라.
범위 실행가능성은 재생성 대상이 아니라 자동 보정 대상이다.
LLM 에 되묻거나 재생성시키지 마라. 코드가 조용히 고치고 내역만 남긴다.

보정 내역은 validation_logs.adjusted_bounds 에,
보정 전 원본은 spec_universe.weight_min_raw / weight_max_raw 에 보존해라.
두 컬럼은 이미 스키마에 있다.

[테스트 — 기대효과 검증 항목이다]
무작위 범위 조합 1000건을 생성해서 다음을 단언해라. 기획서 5.1의 검증 방법 그대로다.
- 보정 후 불변식 Σmin ≤ 1−cash_min ≤ Σmax 가 항상 성립한다 (실행가능성 100%)
- 재생성 호출이 0회다
- 보정이 일어난 경우 adjusted_bounds 에 기록이 남는다
- 원본값이 weight_min_raw / weight_max_raw 에 보존된다
case A 와 case B 가 각각 최소 한 번씩은 발생하도록 생성 범위를 잡아라.

[4단 순서]
스키마 → 참조 → 논리 → (범위 보정) → 하드캡 클램프 순서를 지켜라.
2단 참조 검증은 etf_master 를 조회한다. 1단계에서 남긴 상장폐지 종목이
여기서 차단되는 테스트를 하나 넣어라 — 11월 데모 실패 장면 3에 그대로 쓴다.
```

## 4단계 · 하드캡 엔진과 버전 관리

```
docs/m2-algorithms.md 6장의 FN-305 · FN-307 · FN-308 에 따라
하드캡 엔진과 버전 관리를 구현해라.

  기존 Spec 은 승인 시점의 hardcap_version 을 계속 참조한다

사용자가 한도를 지정하면 그 값을 쓰되 하드캡을 넘을 수 없고,
지정하지 않으면 하드캡 범위 안에서 LLM 제안값을 쓴다.

[주의]
하드캡 v0.1 의 실제 수치는 아직 팀 미확정이다(알려진 설계 구멍 ②).
현재 시드에 들어간 보수적 임시값을 그대로 쓰고,
수치를 바꾸거나 새로 정하지 마라. 구조만 완성한다.
