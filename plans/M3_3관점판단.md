## 1. 확정 수치 (변경 금지, 2026-09-08)

- 신호 통합: `m = Σ w_k·s_k` → `s = tanh(m / 0.5)` → `|s| < 0.10` 이면 `s = 0`
- 검산표: m = -1.00 / -0.50 / -0.25 / -0.05 / +0.05 / +0.25 / +0.50 / +1.00
  → s = -0.96 / -0.76 / -0.46 / 0 / 0 / +0.46 / +0.76 / +0.96
- Hedge: `L_k = (p_k − y)²` (Brier), η = 0.5 · 초기 1/3 균등 · floor 0.10 · 윈도우 60거래일 · 매 거래일, 전날까지 확정된 실현치만
- **Hedge 해석 확정(2026-09-12)**: 평가 윈도우는 **롤링 재계산**이다. 매 거래일 1/3 균등에서 시작해 최근 60거래일 손실을 다시 적용한다 — 상태가 없어 `as_of`만 있으면 언제든 같은 값이 나오고, 백테스트를 중간부터 재실행해도 일치한다
  - 곱셈 갱신은 지수가 합으로 접힌다: `Π_t exp(−η·L_k,t) = exp(−η·Σ_t L_k,t)` → 일자별 루프가 필요 없고 관점별 손실 합 `S_k` 하나면 된다
  - **하한은 마지막에 한 번만, water-filling으로.** 상세설계서 1.5.5 의사코드의 "클립 후 재정규화"를 그대로 쓰면 하한이 깨진다: `(0.95, 0.03, 0.02)` → 클립 `(0.95, 0.10, 0.10)` 합 1.15 → 재정규화 `(0.826, 0.087, 0.087)` 로 둘이 다시 0.10 밑이다. water-filling은 `(0.80, 0.10, 0.10)` 을 낸다
  - FN-409 초기 가중치에 별도 분기가 필요 없다 — 손실 이력이 비면 `S_k`가 전부 0이라 자연히 1/3 균등이 나온다
- 백테스트 구간 2023-01-01 ~ 2025-12-31, 워밍업 첫 250거래일, 성과 집계 2024-01 ~ 2025-12

## 3. as_of 가드 취급 요령 (저장소 실물 확인)

| 형태 | 잡히나 | 근거 |
|---|---|---|
| `#` 주석 안의 테이블명 | **안 잡힘** | `ast.parse`가 주석을 노드로 만들지 않는다 |
| docstring 안의 테이블명 | **잡힘** | docstring은 `ast.Constant` 문자열이다 |
| f-string 조각 | **잡힘** | 조각도 `ast.Constant`로 노출된다 |
| `from app.repositories.feature_store import get_features` | **통과** | 가드는 `alias.name`/`asname`만 보고 `ImportFrom.module`은 안 본다 |

실무 규칙 둘.

1. `app/views/**` 의 설명은 docstring이 아니라 **`#` 주석**에 쓴다 (현서가 `contracts/view_weights.py` 상단에서 쓴 수법 그대로).
2. 세 테이블 INSERT/UPSERT SQL은 `app/repositories/` 안에만 둔다. `app/views/**` 에서 모듈 경로로 import 해 호출하는 것은 자유다.

## 5. 의존성·테스트 격리 방침 — **Q6 (c)안 확정·구현 완료**

- `integrator` · `hedge` · `base` 는 **stdlib(`math`) + pydantic 외 의존성 없이** 순수 함수로 격리한다 → 검산표·수렴 테스트가 CI에서 항상 돈다. numpy도 쓰지 않는다 — base dependencies에 없어서, 끌어들이면 격리 전제가 깨진다
- 모델 학습·추론(LightGBM/SHAP)과 KF-DeBERTa만 `requires_ml` 마커로 뺀다 (현서의 `requires_ollama` 선례를 그대로 따른다)
- CI 설치 스텝(`pip install -e ".[dev]"`)을 건드리지 않는다. pytest 스텝의 `-m` 표현식만 `not requires_ollama and not requires_ml` 로 바꿨다
- **torch는 CPU 전용 휠.** `--extra-index-url https://download.pytorch.org/whl/cpu` 가 `backend/Dockerfile` 과 README 양쪽에 있어야 한다 — `pyproject.toml` 로는 패키지별 인덱스를 못 박는다. 빠지면 CUDA 휠(2.5GB+)이 잡혀 단일 이미지 결정이 무효가 된다
- **Dockerfile은 `.[dev]` 그대로 둔다 (S2-fix, 2026-09-12).** 실측해 보니 CPU 휠이어도 site-packages 933MB · torch 769MB였고, `ci.yml` 이 `docker compose up` 으로 이미지를 빌드하는데 buildx 레이어 캐시가 없어 PR마다 그만큼을 새로 받게 된다. 지금 이미지 안에서 ML을 쓰는 코드가 하나도 없다(`train_model`·`daily_judge` 는 스텁, Hedge·통합기는 `math` 만, 개발은 호스트 venv). **이미지 반영은 T4(LightGBM)에서 실제로 필요해질 때 buildx 캐시 도입과 함께.** 이미지를 쪼개지 않는다는 결정 자체는 유효하다
- **`backend/tests/conftest.py`에 autouse 픽스처가 없다**는 걸 확인했다. `engine`·`portfolio_id`·`make_user`·`client` 중 아무것도 요청하지 않는 테스트 파일은 postgres 없이 그냥 돈다 → `test_integrator.py`·`test_hedge.py`는 픽스처 없이 짠다. conftest를 고치거나 새로 만들지 않는다
- DB가 필요한 테스트는 `portfolio_id` 픽스처 패턴(FK 체인 최소 생성 → teardown 역순 삭제)을 그대로 빌린다
